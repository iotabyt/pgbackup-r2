With a managed database, there's no server of your own to run the nightly container on. So a scheduled GitHub Actions workflow takes the backups, and your laptop runs the drills.

Pick your provider for the connection details and a walkthrough:

<CardGrid>
  <LinkCard title="Neon" description="Tested on real data, with Postgres 18." href="/guides/neon/" />
  <LinkCard title="Supabase" description="Not tested yet. What should work, and what to watch for." href="/guides/supabase/" />

Anything else (Crunchy Bridge, RDS and so on) works the same way, as long as the database meets the rules below.

## The workflow

[`examples/nightly-backup.yml`](https://github.com/iotabyt/pgbackup-r2/blob/main/examples/nightly-backup.yml) is a complete one. Copy it to `.github/workflows/` in a **private** repo. The core of it:

```yaml
on:
  schedule:
    - cron: "17 2 * * *"
jobs:
  backup:
    runs-on: ubuntu-24.04
    steps:
      - env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
          AGE_RECIPIENTS: ${{ secrets.AGE_RECIPIENTS }}   # the PUBLIC key only
          S3_ENDPOINT: ${{ secrets.R2_ENDPOINT }}
          S3_BUCKET: ${{ secrets.R2_BUCKET }}
          S3_PREFIX: myapp
          AWS_ACCESS_KEY_ID: ${{ secrets.R2_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.R2_SECRET_ACCESS_KEY }}
        run: |
          docker run --rm -e DATABASE_URL -e AGE_RECIPIENTS -e S3_ENDPOINT -e S3_BUCKET \
            -e S3_PREFIX -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY \
            ghcr.io/iotabyt/pgbackup-r2:pg17 backup
```

- **Set the image tag to your Postgres major version** (`pg16`, `pg17`, `pg18` or `pg19`). Run `SHOW server_version;` to check. See [Postgres versions](/concepts/postgres-versions/).
- **Only the public key goes in the secrets.** The workflow can write backups but never read them. The private key stays in your password manager and on your laptop.
- **`-e NAME` with no value** passes the variable through from the step's environment, so secrets never appear on a command line.
- **Set a heartbeat.** Scheduled runs can start some minutes late, or fail, and a heartbeat (`HEARTBEAT_URL`) notices when backups stop. (GitHub also disables scheduled workflows after 60 days without activity, but only in **public** repos. A private repo, which is what you want here, isn't affected.)

## The database must accept outside connections

GitHub's runners connect from changing addresses all over Azure, so an IP allowlist won't let them in unless it allows them all.

- **Use a direct or session-mode connection.** `pg_dump` needs a real session, so a transaction-mode pooler won't do.
- **Use TLS.** Managed providers require it anyway: keep `?sslmode=require` on the URL.
- **Use a user that can read every table** you want in the backup.

The provider pages say what that means for [Neon](/guides/neon/) and [Supabase](/guides/supabase/).

<Aside type="caution">
Drills need the **private** key. Run them from your laptop, or from a separate workflow in a separate repo or environment: see [Monthly drills](/guides/monthly-drills/). Never put the private key next to the backup workflow.
</Aside>
